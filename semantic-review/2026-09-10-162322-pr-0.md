# AI Clipper frontend workspace rewrite: coherent screens with a blocked launch handoff

The rewrite gives the dashboard, three-step create flow, live job room, project inspector, library, operations console, marketing screen, and pricing screen distinct routes and layouts. The frontend uses the current presets, process/upload, job, project, clip-edit, download, and admin contracts; the backend suite passes 24 tests. The main production path is blocked by a non-functional direction-step CTA, while project trimming can expose values the edit API rejects and reload recovery loses part of the saved brief. **Watch for:** **confirmed blocker** — “Review launch brief” does nothing; **confirmed high-risk** — the workspace APIs and browser-held provider keys assume a local-only trust boundary; **confirmed medium-risk** — invalid trim values and stale/deleted-job recovery paths remain.

**Verdict**: NEEDS_CHANGES

## High-level view

Hash routes and active-screen CSS make the dashboard, create, job, project, library, operations, marketing, and pricing surfaces materially distinct. The create flow has a coherent source → direction → launch brief model, but its primary direction CTA is not wired, and the URL field visually supplies `https://` while validation requires the user to type the scheme.

The pipeline handoff matches the current API shapes, and the job room supports GET hydration plus SSE/polling. Saved upload briefs do not restore their options into the job room, missing/deleted jobs are not terminalized, and provider credentials remain browser-held and browser-supplied.

The project workspace consumes the public clip DTO, re-renders through the current edit endpoint, and builds individual and ZIP download routes. The boundary controls are not bounded to the backend’s source-duration rule, and a failed ZIP request navigates the SPA to a raw error response.

The library and operations screens are separate and their endpoint names match the backend. The library’s score column is backed by a field the list DTO does not return, the first 100 projects are the entire inventory, and dashboard/job status presentation omits active backend states. Operations still depends on an explicit server-side authentication posture.

<summary>Issues (10)</summary>

1. **Blocker — dead direction-step launch CTA (confirmed)** — `#directionContinue` has no `data-create-jump` attribute, ref binding, or click handler, so the normal create flow cannot reach the launch brief. Wire it to the existing review transition and cover the click path.
2. **High — public workspace and browser-held credentials (confirmed)** — processing, project listing/deletion, and project media APIs have no user/tenant authentication, while provider and admin keys live in `sessionStorage` and provider keys are sent from the browser. Enforce an explicit local-only boundary or add authentication/tenant scoping and keep provider secrets server-side where possible.
3. **Medium — trim control can submit an invalid source end (confirmed)** — the project range max can exceed the known source duration, but `/api/clips/{clip_id}/edit` rejects `custom_end` beyond that duration. Cap the range and clamp the payload before submitting.
4. **Medium — reload recovery loses upload brief context (confirmed)** — initialization restores options only when a URL exists, so a reloaded upload job can show the wrong output mode and channel selection is never persisted. Restore all brief fields independently of source type.
5. **Medium — missing/deleted jobs can poll forever (confirmed)** — fallback polling ignores every error, and hydration does not clear `AI_CLIPPER_ACTIVE_JOB` on 404 or on a terminal state loaded by GET. Stop polling and clear the stale ID when the job is gone or already terminal.
6. **Medium — ZIP download errors eject the user from the workspace (confirmed)** — `Download set` assigns `window.location.href` directly even though the backend returns 400 for a project with no clips. Disable the action until clips exist or preserve the project screen while handling the error.
7. **Low — active status mapping is incomplete (confirmed)** — dashboard attention counts only `FAILED`, `PROCESSING`, and `QUEUED`, while the backend emits `DOWNLOADING`, `TRANSCRIBING`, `ANALYZING`, and `CLIPPING`; the job stage mapper also marks ingestion complete during downloading. Normalize all active states before presenting progress and attention counts.
8. **Low — URL field rejects its own affordance (confirmed)** — the UI supplies an `https://` prefix and a scheme-less placeholder, but validation requires the typed value to include `http://` or `https://`. Either prepend the scheme before validation or remove the visual prefix/adjust the placeholder.
9. **Low — library summary assumes fields the API does not return (confirmed)** — `/api/projects` exposes `clips_count` but not `average_score`, so every project row displays `—`; fixed `limit=100` also silently hides older projects. Add the aggregate/pagination contract or compute and page the data explicitly.
10. **Low — no frontend behavior coverage (confirmed)** — the passing suite exercises backend contracts but not the create CTA, hash routing, reload/retry, SSE fallback, project boundary validation, download failures, or admin interactions. Add browser or DOM-level tests for those paths.

### Guided creation flow and screen topology

The source step reaches `direction` through the URL form and upload button. The next primary action is not equivalent: `frontend/index.html:128` renders `id="directionContinue"` without `data-create-jump`, while `bindCreate` only binds `sourceContinue`, `uploadContinue`, and elements matching `[data-create-jump]` (`frontend/app.js:845-862`). With a valid source selected, clicking “Review launch brief” has no effect; the stepper’s smaller Launch control is the only route into review. **Confidence: confirmed.**

The URL affordance has a separate contract mismatch. The source field renders a literal `https://` prefix and a `youtube.com/watch?v=...` placeholder (`frontend/index.html:118`), but `validateSource` passes the raw input to `new URL` and accepts only `http:` or `https:` (`frontend/app.js:516-525`). A user following the placeholder and omitting the scheme receives “Enter a valid public video URL.” **Confidence: confirmed.**

### Pipeline contract, credentials, and saved brief recovery

The request names match the current handlers: JSON URL jobs send `url`, provider keys, subtitle/layout/aspect options, and `target_clips`; uploads send those fields as multipart values; presets supply the option IDs and limits. Job GET/SSE snapshots expose the fields consumed by the room.

The trust boundary is materially weaker than the visual “workspace” framing suggests. `frontend/app.js:283-296` attaches the admin key to admin URLs and `frontend/app.js:571-580` sends provider keys from browser storage with every new job. The current backend protects only `/api/admin`; processing, project listing/deletion, and media/download routes are public (`backend/main.py:280-305`, `401-415`, `449-451`, `539-548`). With empty `REQUIRE_ADMIN_KEY` and `ADMIN_API_KEY`, `verify_admin_access` also permits the destructive admin routes (`backend/main.py:557-572`). A remotely reachable deployment could accept work, read/delete another workspace’s projects, and expose browser-held credentials. Use an explicit local-only guard or authentication/tenant ownership, and keep provider secrets server-side where possible. **Confidence: confirmed.**

The active job ID is persisted after submission and the last brief is stored without provider keys, but restoration is asymmetric: startup restores `state.create.options` only inside `if (state.job.lastSubmission?.url)` (`frontend/app.js:889-900`). A reloaded upload job retains its options in storage while the live create state remains default, so `renderJob` can report the wrong aspect ratio (`frontend/app.js:697`); `channel` is not persisted at all. The retry path reapplies options later, but the review UI can still show the wrong channel direction. **Confidence: confirmed.**

### Durable job room and operations lifecycle

The terminal assumptions break when state is loaded rather than received as a live update. `hydrateJob` renders a terminal snapshot but does not clear `AI_CLIPPER_ACTIVE_JOB`; its 404 branch also redirects without clearing it (`frontend/app.js:675-682`). If an administrator removes the job or a finished record is cleared, the fallback interval catches the 404 forever (`frontend/app.js:652-655`) and every reload can retry hydration for the same stale ID. Treat not-found as a terminal “removed” state, stop the monitor, and clear persisted recovery state. **Confidence: confirmed.**

Backend workers emit `PROCESSING`, `DOWNLOADING`, `TRANSCRIBING`, `ANALYZING`, `CLIPPING`, and terminal states (`backend/services/job_manager.py:180-298`), but `renderDashboard` counts only three active/attention values (`frontend/app.js:474-479`). `jobStageState` has no explicit downloading or processing stage, so its fallback marks ingest complete while downloading is active (`frontend/app.js:700-710`). Progress and “Needs attention” are therefore misleading during common stages. **Confidence: confirmed.**

The Operations action URLs and response fields match the current admin handlers, and the destructive job action is confirmation-gated. Its security still inherits the public/default configuration gap described above. **Confidence: confirmed.**

### Project review, editing, and downloads

The edit payload uses the backend’s `subtitle_preset`, `layout_mode`, `aspect_ratio`, `custom_start`, `custom_end`, and optional `custom_words` fields, and current generated clip filenames match the individual download URL convention.

The boundary editor can expose a value the backend rejects. `renderSelectedClip` sets both range maxima to `Math.max(end + 15, project.duration || 30)` (`frontend/app.js:737`), so a clip near the end of a known source gets a slider range beyond `project.duration`. The backend rejects `end > duration + 0.5` (`backend/main.py:509-510`). The user can move the control into that invalid area and receive a re-render error while remaining inside the UI’s range. **Confidence: confirmed.**

`Download set` is wired to `/api/projects/{project_id}/download-all` but bypasses `apiRequest` and UI error handling (`frontend/app.js:865`). The backend returns 400 when a project has no clips (`backend/main.py:452-458`), which is reachable for a processing project listed in the library; the browser then navigates away from the SPA to the raw error response. **Confidence: confirmed.**

### Library inventory and summary data

`ProjectModel.public_view` returns `clips_count` but not `average_score` (`backend/db/models.py:55-72`), while `projectRow` reads `project.average_score` (`frontend/app.js:463-468`), so the score column is permanently blank. The client always requests `limit=100&offset=0` (`frontend/app.js:443-446`) even though the backend accepts offsets, silently truncating larger workspaces. **Confidence: confirmed.**

### Test coverage and validation

The existing backend suite passes with 24 tests, including presets, project/ZIP APIs, job creation, crash recovery, admin protection, upload limits, and security helpers. No browser test runner is installed (`node` and system `pytest` are unavailable; the repository virtualenv ran the backend suite), and there are no frontend behavior tests in the current tree.

**Not tested:** the dead direction CTA, no-scheme URL entry, hash back/forward, upload-job reload/retry, SSE disconnect-to-polling, deleted-job recovery, trim values near source end, ZIP errors on processing projects, and Operations actions through the browser. **Confidence: confirmed.**
